# Chunk 3: secure synthetic uploads and deletion

Date: 2026-09-26. User authorized storage/upload implementation, tests and local migration validation; no commit, Chunk 4, clinical processing or live integration.

## Boundary

Normal `create_app()` still has no upload routes, including with `MEDLM_ENVIRONMENT=test`. Only an explicitly injected `SyntheticUploads` object in a test-environment application mounts these routes. It requires an operator-supplied checksum allowlist of controlled generated fixtures; both declared and actual bytes must match. A request flag, purpose label or acknowledgement cannot enable medical uploads. There is no normal Flutter upload screen, picker, service registration or production enable flag. Flutter's test-harness adapter exercises the same authenticated backend contract without retaining files.

Phase 1 auth routes and response shapes remain intact. Chunk 2 session checks remain authoritative. One shared transaction advisory lock now orders local session revocation and final upload writes; the owned user row is locked against account disablement. Browser request principals carry the earlier provider/app expiry. Expiry is rechecked after body receipt and decoding; work ordered before logout can finish before logout commits, but later writes fail. No upstream service is called by storage or deletion.

## Contract and persistence

The harness exposes POST `/api/v1/uploads`, PUT `/{id}/content`, POST `/{id}/complete`, GET/DELETE `/{id}`, GET `/{id}/preview` and GET `/{id}/receipts`. Paths after the first are relative to `/api/v1/uploads`. See `contracts/synthetic-openapi.json`; the normal `contracts/openapi.json` remains unchanged.

Creation requires a UUID `Idempotency-Key`, reviewed test notice `consent_version=synthetic-v1`, source SHA-256, size, MIME, document kind and explicit review choice. Migration 0004 adds nullable immutable request key/hash/source checksum fields to preserve legacy rows. Same key/payload returns existing metadata with **no ticket**; changed payload returns 409. Recovering a lost ticket means deleting the abandoned intent and creating a new one, never replaying a stored capability. Complete is intrinsically idempotent by upload/source checksum (also requires a syntactically valid idempotency header); first completion and deletion require quoted version `If-Match`. Already deleting returns 202, already deleted returns 204. A receipt list can remain empty while deletion is pending.

Tickets are random, hash-only in the DB, owner bound, single use and expire within five minutes. Reservation commits inventory before receiving bytes, so crashes cannot leave an uninventoried normal write. Stream input is bounded by declaration/10 MiB and a 30-second transfer deadline, with four transfer slots per application instance. Hash allowlisting precedes decoding; existing Pillow MIME/decode/pixel/animation checks and metadata-free PNG re-encoding remain required. Original bytes and filenames never reach disk. A failed transfer queues deletion; an abandoned reservation expires independently at ticket expiry. Five outstanding intents and 30 MiB declared input per owner are enforced under a per-owner lock.

Local storage encrypts owner UUID plus sanitized bytes with a separate Fernet key, uses exclusive UUID-named files and fsync, and rejects overwrite/path traversal. Keys never come from clients. Reads verify the encrypted owner; API/RLS ownership checks precede storage access. Preview requires accepted, retained, unexpired state and returns PNG with no-store/nosniff. Non-review completion queues immediate deletion. Review retention defaults to one hour in the harness, configurable downward/upward only at harness construction within the schema's 24-hour bound; retries never extend it.

## Independent safeguards

An explicitly provisioned `medlm_upload_worker` role has table-specific upload maintenance grants and role-specific FORCE RLS policies, with no owner/BYPASSRLS, auth or clinical-table access. API credentials do not have this role. `database/synthetic_upload_grants.sql` is opt-in for disposable harness databases; default runtime grants still deny uploads. Worker ownership comes from DB inventory, never a submitted user ID.

API update grants name only lifecycle/acceptance columns; it cannot mark objects purged, complete deletion jobs or insert receipts. The worker cannot insert uploads/objects or update immutable audit/receipt records. Ledger cleanup uses the common maintenance lock rather than requiring update privileges for row-locking immutable records. Downgrading 0004 preserves earlier tables/records but discards its request metadata and policies; stop the Chunk 3 runtime and remove opt-in grants before downgrade. This is not a production rollback procedure.

Three independent command modes can run in separate processes: deletion jobs with persistent leases/fencing/retries; an expiry/cancellation sweep that ignores queue state; and reconciliation against actual object keys plus deletion receipts. All local writers/reconcilers share a DB advisory lock around filesystem operations, preventing a stale writer from recreating deleted bytes. Job completion conditionally checks its current lease/fence while holding locks. The sweep continues to purge when the queue is stalled. Batches are limited to 100, local directory enumeration to 10,000 entries; this serialized adapter is deliberately for low-volume synthetic validation.

Actual unlink and a separate existence check precede any purge marker or receipt. Receipt-writing failure leaves deletion unconfirmed and blocks admission. Receipts contain opaque object UUID, verification and expiry times only; public responses omit object keys and owners. They assert absence in the local adapter namespace, not forensic disk erasure or deletion of provider/backups.

A separately located encrypted deletion-ledger directory is written before publishing the DB receipt and is **excluded from DB/image snapshot restoration**. Local read/write checks refuse tombstoned keys. Reconciliation reimports ledger entries and removes restored objects. Both receipt copies expire after 90 days; database backup windows must be shorter (the architecture proposes 30 days). Restoring the ledger itself to an older snapshot is prohibited; losing it requires keeping uploads/preview disabled until recovery. The tests simulate restored object bytes and a missing DB receipt relation, not a managed-provider disaster recovery drill.

New intent/transfer admission requires all three safeguards to have a successful run within five minutes, with no reported overdue inventory. Failed/stale runs deny admission. Commands return only health counts and a failing exit code for a failed single run. OS scheduling/monitoring is an operational requirement: run each independently at least every five minutes, target deletion within 15 minutes, alert and stop admission on failure. No Windows service, cloud scheduler or monitoring deployment is installed by this chunk. A stopped host cannot execute deletion; no production retention guarantee is claimed.

Maintenance removes bounded batches of expired audit/receipt/run records (90/90/30 days) and deleted upload metadata after 90 days. Unpurged inventory still blocks account cascades. Account deletion UI/workflow is outside this chunk. Interrupted receipt files, disk errors and missing encryption keys fail closed; support recovery remains an operational responsibility.

## Validation and limits

Real disposable PostgreSQL tests use API and worker roles separately. Tests cover old migrations, default app denial, ownership, CSRF, retries, races, format validation, interrupted writes, retention, false-success deletion, receipt re-erasure, worker commands and contract separation. Flutter tests cover authenticated binary transport, server URL distrust, completion/version headers, logout/cancellation, no stored image state, preview errors and deletion polling. Full Flutter UI integration, physical-device auth/storage, live Supabase/private buckets, deployment scheduling and load/codec isolation remain separate release gates.

No packages added. Official references checked 2026-09-26: [PostgreSQL row security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html), [Pillow image validation](https://pillow.readthedocs.io/en/stable/reference/Image.html). Installed Starlette request streaming code was used; the official requests page was unavailable during this check. No assumptions about a live Supabase Storage API were needed.
